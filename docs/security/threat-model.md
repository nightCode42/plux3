# Threat Model

The STRIDE threat model required by `SEC-000` is established in P6 and reviewed at the end of every phase from then on. Until P6, each phase records its delta here (DoD-6): what it adds to the attack surface, the threats, and the mitigations with the requirement or test that holds them.

## P1 — Schema and compiler

**Scope.** Project documents (JSON in the Git layout), the compiler and `plux validate`/`build` on developer machines and CI, the bundle format and its Go verifier, PXL programs. Nothing in P1 is networked or signed; bundles are not yet delivered to devices.

**Trust boundaries.** Documents are untrusted input to the compiler: they come from contributors, Studio users and, later, AI assistance. Bundles are untrusted input to every reader, including the runtime from P3.

| STRIDE | Threat | Mitigation | Evidence |
|---|---|---|---|
| Tampering, DoS | A crafted document crashes the compiler, exhausts memory or makes it run for long | Strict I-JSON parser, file-size, depth, string, expression and nesting limits from the registry (`LIM-001`); PXL constant folding bounded by the operation budget; panics recovered as `PLX-2201` | `FuzzCompile`, `FuzzValidatePage`, PXL and JCS fuzz targets, nightly fuzz workflow (`CMP-052`, `QA-004`) |
| Elevation of privilege | Executable code smuggled into a bundle | Only PXL bytecode and action graphs are executable; assets and unknown sections starting with native, script, Dart snapshot or WebAssembly signatures are refused; SVG scripts refused (`SEC-054`, `PLX-1503`) | `TestInvalidProjects` (executable asset, SVG script), `bundle` tests |
| Tampering, DoS | A crafted bundle exploits a reader | Section hashes, bounds and a schema-driven FlatBuffers verifier with depth and table limits before any accessor runs (`BND-006`); PXL programs verified on decode; zstd transport bounded by the declared size (`BND-007`) | `FuzzVerifyPage`, `FuzzRead`, mutation test, Dart decoder over the golden bundles |
| Information disclosure | Secrets or sensitive values end up in bundles, which are readable on devices | Secret-like literals (`PLX-1500`), sensitive state sent to analytics (`PLX-1501`), `http:` URLs (`PLX-1502`); diagnostics never repeat a suspected credential | `TestInvalidProjects`, `TestDiagnosticsDoNotEchoCredentials` |
| Tampering | Two different styles or programs share a 64-bit content ID and one silently replaces the other | A collision is a compile error (`PLX-2202`) | encoder check |
| Spoofing, Repudiation | A modified bundle is taken for a published one | Out of scope in P1: bundle hashes give integrity only. Signing and TUF metadata arrive in P2/P6 (`SEC-050`–`SEC-052`); the runtime never loads unverified bundles | — |
| Tampering (supply chain) | A compromised code generator or dependency | flatc built from source at the pinned tag commit; new dependencies allowlisted by ADR; reproducible builds (`CI-006`); goldens reproduced on three platforms (`CMP-002`) | `go-reproducible`, `go-determinism` |

**Residual risks and follow-ups (P1).** The Dart runtime's FlatBuffers verifier arrives in P3 (`SEC-052`); until then Dart only checks the container. Manifest, DPoP and attestation parsing are fuzzed from P2/P6 (`QA-004`). Regular expressions in PXL (`matches`) arrive in P5 and need a bounded engine.

## P2 — Backend core

**Scope.** `plux-server` with its api and worker roles, the ConnectRPC/HTTP API, PostgreSQL, object storage, Valkey, the durable job queue, the signing abstraction (Vault Transit and the development file backend), device registration and the manifest, deltas, telemetry intake, the `plux` CLI against a server, the Compose stack, container images and the release pipeline.

**Trust boundaries.** (1) Internet → api role: every request is untrusted — Studio users, CLI and CI callers, devices. (2) api role → PostgreSQL, S3, Valkey: trusted stores, but every tenant query runs under row-level security. (3) api role → worker: only through jobs in the database; only the worker holds a signer. (4) Server → outbound hosts (OIDC discovery, CI federation keys, malware scanner): the destination may be attacker-influenced. (5) Release pipeline → users installing images and binaries.

| STRIDE | Threat | Mitigation | Evidence |
|---|---|---|---|
| Spoofing | Password guessing or credential stuffing against Studio accounts | Argon2id, decoy hash for unknown addresses, per-account throttling (`auth.failedSignIns`), second factor (TOTP, WebAuthn) required for the capabilities of `SEC-100`, hashed challenges closing after five wrong codes | `internal/auth` tests (`SEC-100`, `SEC-101`) |
| Spoofing | A stolen session or cross-site request | `__Host-` cookies, CSRF tokens bound to the session, cookie domain refused in configuration | `internal/auth`, `internal/api` tests (`SEC-101`) |
| Spoofing | A leaked CLI or CI token | Personal access tokens with fixed scopes never above the creator's; CI federation verified against the provider's keys with installation-bounded subject patterns; tokens stored only as hashes; the CLI keeps its token in the OS credential store ([ADR-0028](../adr/0028-cli-credential-storage.md)) | `internal/auth`, `cmd/plux` tests (`SEC-102`, `CLI-002`) |
| Spoofing | A forged device or a device replaying another's token | Device secrets stored as hashes, 15-minute access tokens, device tokens open only the four device procedures. Hardware binding (DPoP, attestation) arrives in P6 | `internal/device` tests (`GOV-010`); device binding P6 |
| Elevation of privilege | One organisation reads or writes another's data | PostgreSQL row-level security on every tenant table; the tenant setting is local to its transaction; RBAC checked per procedure; page tokens bound to procedure, scope, filter and order | `storage` and `tenancy` integration tests (`SRV-020`, `SRV-022`, `GOV-001`) |
| Elevation of privilege | The internet-facing api role signs arbitrary content | Only the worker role gets a signer (`CrypterOnly` for the api role, ADR-0006); signing only after a compile with no error or unacknowledged warning; the file backend refuses production environments (`SEC-056`) | `internal/signing`, `internal/release` tests (`SEC-120`) |
| Tampering | A modified bundle, delta or manifest served by a compromised CDN or store | Bundles addressed and signed by bundle hash; deltas refused when the result's hash differs (`PLX-3011`); manifests signed as RFC 8785 canonical JSON with a seven-day expiry. Device verification is P3/P6 | `delta` property and fuzz tests, `TestPublishWithTheCLIAndSyncADevice` (`REL-020`–`REL-033`, `BND-002`) |
| Tampering | A release differs from what was reviewed | Build once, promote: a release is recompiled from its versions' sources and must be byte-identical (`PLX-8050`); rollback is a new sequence with old content | `internal/release` tests (`REL-001`–`REL-007`) |
| Repudiation | An administrator denies a change | Append-only audit chain per organisation, a trigger refusing `UPDATE`/`DELETE`/`TRUNCATE`, request metadata from the edge, lock takeovers recorded with both parties | `internal/audit` tests (`SEC-140`) |
| Information disclosure | Secrets, tokens or sensitive fields in logs, traces, metrics or errors | Redacting logger by attribute name and `Sensitive` interface, fixed metric label sets, unrecognised failures become one internal error with an incident ID, telemetry fields that look sensitive refused, secrets sealed per row | `internal/observability`, `internal/api`, `internal/telemetry` tests (`SRV-006`, `SEC-106`, `OBS-001`) |
| Information disclosure | Secrets committed in documents | Secret-like literals by pattern and entropy refuse the publish (`SEC-107`) | `internal/compiler` tests |
| Tampering, Information disclosure | Server-side request forgery through OIDC discovery, federation keys or scanner addresses | SSRF-safe client checking the resolved address at dial time and on every redirect, response size limits | `internal/httpx` tests (`SEC-105`) |
| DoS | Oversized requests, floods, decompression bombs | Request, response and stream sizes and per-address, per-account and per-device rate limits from the limits registry; zstd bounded by the declared size; asset pixel and size limits; transcoders in fresh WebAssembly instances | `internal/api`, `delta`, `media` tests and `FuzzMedia` (`SEC-104`, `LIM-001`, `SRV-065`) |
| Tampering (supply chain) | A compromised image, binary or dependency reaches users | Reproducible binaries (`CI-006`), distroless images pinned by digest and running as non-root, CycloneDX SBOMs, cosign keyless signatures and SLSA level 3 provenance for images and archives; `install.sh` verifies checksums and the signature | `release.yml`, `image.yml` (`DEP-001`, `CI-004`) |
| Elevation of privilege | A container escape or lateral movement in the Compose stack | Read-only root file systems, all capabilities dropped, `no-new-privileges`, non-root users, ports bound to `127.0.0.1` | `compose.yaml`, `backend/Dockerfile` (`SEC-108`, `DEP-002`) |

**Residual risks and follow-ups (P2).** Device binding (DPoP, attestation) and the full TUF role set with rotation arrive in P6 (`SEC-050`–`SEC-056`); until then a stolen device secret works from any device, and P2 has no call to revoke one registration (device lifecycle arrives in P6). The runtime's manifest and bundle verification is P3. Studio's browser protections (nonce CSP, Trusted Types) arrive with Studio in P11. The load-test Compose overlay trusts Docker's private ranges as proxies and must never be used outside a load test. The ASVS 5.0 L2 and API Top 10 checklist for the server is in [asvs-server.md](asvs-server.md).
