## 1. Goal and exit criteria

**Goal (spec §5.1).** P5 delivers:

- the rest of the action catalogue on P4's engine core (Appendix D), and the engine's
  remaining features: every trigger, every concurrency policy, cancellation and detached
  runs, retries, optimistic updates, the full error chain, traces and reusable flows;
- the PXL VM at its performance target, with the `regex` and `phone` library groups;
- scoped state on Riverpod with fine-grained rebuilds: every scope, typed writes, computed
  entries, watchers, persistence and versioned migrations;
- forms and validators, including asynchronous validators;
- data sources (REST, GraphQL, WebSocket, Server-Sent Events, local database, static) with
  caching, pagination, streams, uploads and downloads, and an encrypted offline outbox;
- a local database behind an adapter interface, Drift on SQLite (SQLCipher) by default;
- animations: implicit, timelines, enter and exit transitions, Hero, Lottie and Rive,
  reduce motion, and custom page transitions (`NAV-010`);
- Plux Test for declarative scenario tests, and the reference host apps (`DX-004`).

**Exit criteria.**

1. The spec's criterion: a complete multi-page flow — login → dashboard → form → result —
   built from JSON alone runs on a device with API calls, local persistence and animations,
   meeting the §30 performance targets (D3 says how those are measured).
2. Definition of Done (spec §5.3) DoD-1 to DoD-9 holds, with the scope and deferrals of §3
   as the maintainer settles them.
3. Every milestone passes the milestone exit gate (§11).
4. The core package stays within its size budgets (`RT-061`: ≤ 4 MiB per App Bundle download
   and ≤ 10 MiB per APK, per ABI; ≤ 3 MiB for the IPA), measured against the round 3
   baseline. Heavy capabilities ship in optional packages (`RT-060`).

## 5. Architecture

Module layout follows spec §6.4: `actions/`, `state/`, `data/`, `db/` and `anim/` in
`plux_flutter/lib/src/`, with optional packages beside the core.

### 5.1 Action engine completion (R1) — ADR-0045

- **Triggers (`ACT-002`):** widget events (all ten kinds); page lifecycle, which the page
  schema already declares (`onInit`, `onEnter`, `onResume`, `onLeave`, `onDispose`); state
  watchers (on a state path, debounced by the trigger's policy); timers (interval and
  one-shot, owned by the page or the app); app lifecycle (resume, pause); push opening (P4
  routes a push, P5 also fires a trigger); host events (`Plux.sendEvent`, `HST-013`); and
  data-source events (`loaded`, `failed`). Handlers already carry `concurrency` and
  `detached` (`eventHandler`, P1); the app document has no triggers yet, so app-level
  watchers, timers, lifecycle, push and host-event triggers are an additive schema change
  in R0.
- **Concurrency (`ACT-003`):** all six policies. The compiler's encoding of an absent
  policy changes from `parallel` to the per-trigger default (`drop` for taps), with a
  `required_features` key so P4 runtimes keep their behaviour (ADR-0039's open point).
- **Cancellation (`ACT-004`):** runs are cancelled with their owner unless `detached`;
  detached runs are bounded by the per-run timeout and owned by the app.
- **Bounds (`ACT-005`):** 10,000 steps per run, `forEach` by list length and
  `action.forEachItems`, per-step and per-run timeouts from the registry.
- **Retries (`ACT-006`):** count, exponential backoff with jitter, retryable error kinds.
- **Optimistic updates (`ACT-007`):** a step's `optimistic` state change is applied before
  the step and rolled back if the step fails (`patchState`, `apiCall`, database writes).
- **Errors (`ACT-020`):** typed kinds; step `onError` → page → plugin → app handlers; an
  unhandled error shows the themed fallback message and is reported. Messages use the
  runtime's built-in strings until P8's localisation.
- **Flows (`ACT-061`):** named graphs with typed inputs and outputs, exported across
  plugins; `callFlow` runs them, with cycle detection at compile time.
- **Control actions:** `switch`, `forEach`, `parallel` (first error cancels the rest),
  `delay`; `trackEvent`, `sync`, `emitEvent`.
- **Traces (`ACT-030`, `ACT-031`):** run ID, trigger, steps with start and end, status,
  redacted inputs and outputs, errors; sensitive values never recorded; `TimelineTask`s for
  `RT-015`.

### 5.2 State engine (R2) — ADR-0046

- Scopes `app`, `plugin`, `page`, `component`, `run` (`STA-001`) as Riverpod providers keyed
  by scope instance; bindings keep `select`-level rebuilds (`STA-010`, `RT-012`).
- `setState`, `patchState`, `resetState`; writes type-checked at compile time and at run
  time for values from outside (`STA-002`).
- Computed entries memoised on their dependencies (`STA-004`); state watchers feed §5.1.
- Persistence `memory`, `session`, `persisted`, `secure` on the built-in store (`STA-003`,
  D5, D6).
- Versioned persisted state (`STA-040`): publish compares with the previous release; a
  type change needs a migration expression or an explicit reset.
- Exposed entries writable from plugins; host accessors see the writes (`STA-030`,
  `HST-021`); host-to-Plux events (`HST-013`), with `plux codegen` generating the send side.

### 5.3 Forms and validators (R3) — ADR-0047

- Form state: fields, values, validators, dirty and touched flags, submit status, errors;
  `validateForm`, `submitForm`, `resetForm`.
- Validators: required, length, range, regex (`pxl.regex.v1`), email, phone by region
  (`pxl.phone.v1`, default region from the device locale), IBAN with checksum, date range,
  decimal precision, custom PXL; asynchronous validators via `apiCall` with debouncing.
- The regex engine and phone metadata in Go and Dart, with shared vectors (D7).

### 5.4 Data layer (R4, R5) — ADR-0048

- **Clients (R4):** REST and GraphQL on the existing `http` clients, base URLs per
  environment (`DAT-003`), the auth delegate's token with refresh on `401` (`HST-010`),
  every request checked against the plugin's network domains (`DAT-030`, `SEC-080`).
- **Mapping (`DAT-004`):** selectors and PXL transforms to the declared type; failures are
  typed errors.
- **Caching (`DAT-010`):** `networkOnly`, `cacheFirst`, `networkFirst`,
  `staleWhileRevalidate`, TTLs, cache keys, optional encryption, the cache limit.
- **Pagination (`DAT-011`):** cursor, page and offset, bound to lists (`WGT-012`).
- **Actions:** `apiCall`, `refreshData`; `api_call` telemetry without payloads.
- **Mocks (`DAT-080`):** the document's mocks with `loading`, `empty`, `error` and `success`
  states, selected by tests and by development builds.
- **Streams (R5, `DAT-012`):** WebSocket and SSE with reconnection, backoff and
  resubscription; `subscribe`, `unsubscribe`; messages as data-source events.
- **Outbox (R5, `DAT-020`):** `offlineCapable` mutations persisted encrypted, replayed in
  order with idempotency keys (D13), with success, failure and conflict events; full outbox
  refused with a typed error (`LIM-004`).
- **Transfers (R5, `DAT-031`):** uploads and downloads with progress, cancellation and size
  limits.

### 5.5 Local database (R6) — ADR-0049

- `PluxDatabaseAdapter` (collections, typed queries, reactive watches, transactions,
  migrations), with the built-in store and `plux_db_drift` (SQLCipher) (`DB-001`, `DB-002`).
- Collections typed with keys, indexes and scope; plugin-private collections namespaced
  (`DB-004`).
- Migrations produced at publish; destructive changes need a plan and an acknowledged
  warning (`DB-005`), reusing P4's acknowledgement of publish warnings.
- `dbInsert`, `dbUpdate`, `dbUpsert`, `dbDelete`, `dbQuery`, watched queries bound to lists
  that rebuild only changed items (`DB-006`); work off the UI isolate (`DB-007`).
- `Plux.wipeData` per plugin or all (`DB-008`); the key-value store and `kvGet`, `kvSet`,
  `kvRemove` (`DB-009`); `logout` signals the host (`HST-010`).
- A custom adapter registered in `PluxConfig` (`DB-003`'s `MUST` half).

### 5.6 Animation (R7) — ADR-0050

- Implicit animation of animatable props (`ANI-001`); timelines from the bundle's timelines
  section with keyframes, curves, stagger, repeat and reverse, controlled by
  `startAnimation` and `controlAnimation` (`ANI-002`); enter and exit transitions
  (`ANI-003`); Hero between Plux pages and between Plux and native Flutter pages
  (`ANI-004`); gesture- and scroll-linked animation with springs (`ANI-006`).
- Reduce motion honoured per animation (`ANI-007`); compiler warnings for expensive
  patterns (`ANI-008`); the `page.animations` budget enforced.
- Custom page transitions from timelines (`NAV-010`).
- `plux_lottie` (dotLottie) and `plux_rive` with state-machine inputs bound to state
  (`ANI-005`).

### 5.7 Device and feedback actions, capabilities (R8) — ADR-0051

- `showSnackbar`, `showToast`, `haptic`, `copyToClipboard` (blocked on secure pages),
  `openUrl` (allowlisted domains, deep links), `share`, `requestPermission`, `pickImage`,
  `capturePhoto`, `pickFile`, `scanCode`, `getLocation`, in the packages D4 settles.
- Capabilities (`SEC-080`): network domains (R4), device APIs, native routes; the app's
  approved set and `PluxConfig.allowedCapabilities` (D12); undeclared operations blocked and
  reported.
- `plux native scan` records the Plux packages a host build installs, and publishing warns
  when a release uses a device action a build lacks.

### 5.8 Tooling (R9) — ADR-0052

- **Plux Test:** scenario schema; `plux test` with JUnit XML; the starter and reference apps
  carry scenarios that CI runs (`TST-001`, `TST-002`).
- **Import:** `plux import openapi` and `plux import graphql` (`DAT-002`); `plux mock`
  serves mock responses from an OpenAPI document (`TST-004`).
- **Codegen and init:** `plux codegen` gains host-to-Plux event senders and writable state
  handles; `plux init` adds optional packages a project uses.

### 5.9 Reference apps and backend (R10)

- `apps/plux_bank` and `apps/plux_express` (spec §33), with their fixtures in
  `schema/testdata/documents`, their flows in the device jobs, and the exit flow
  (login → dashboard → transfer form → result) on the emulator and simulator.
- `test/refapi`: a Go test server for their REST, GraphQL, WebSocket and SSE APIs, started
  by the end-to-end tests as the Plux server is.

## 10. Risks

| Risk | Mitigation |
|---|---|
| P5 is the largest phase so far | Milestones grouped into smaller pull requests (D18); R1 and R2 first, since everything depends on them; scope settled in D1 before code |
| Core size crosses the IPA budget (3 MiB, round 3 at 2.45 MiB) | Heavy capabilities in optional packages; phone metadata measured before it lands; a size check at every milestone, not only at R11 |
| Interpreter and VM overhead | `bench-steps` and the PXL micro-benchmark gate A/B from R0; ADR-0039's synchronous fast path kept |
| Regex divergence between Go and Dart | One engine specification, shared vectors, fuzzing |
| Outbox replays a mutation twice | Idempotency keys, ordered replay, conflict events, tests with a server that drops responses |
| Data at rest exposed | Encryption from D6, keys in Keystore/Keychain, threat-model delta |
| Requests to unapproved domains | Checked before any request leaves; blocked and reported (`PLX-5100`) |
| Third-party plugins (camera, scanner, location) | Optional packages, an ADR each, permissions declared and enforced, missing packages reported at publish |
| Reference apps grow into products | Only P5 features; later parts named in §9 |

## 11. Process

- **Branches and pull requests:** as D18 settles.
- **Milestone exit gate** (the P3 and P4 gate, unchanged):
  1. every `make` gate passes locally, judged by its exit code, not its output;
  2. the end-to-end flows pass at least 40 times with the race detector, and every
     intermittent failure is root-caused;
  3. a dispatched CI run is green in every job;
  4. the milestone's open items are fixed or put to the maintainer;
  5. the hand-off note and the report say what was verified and how.
- **Stops for the maintainer** (AGENTS §7), already known: approving this plan and §2; the
  spec changes and ADRs of R0; every new dependency; the coverage floors of new packages;
  new CI jobs or gates; anything touching key handling or encryption (D6); the capability
  model (D12).
- **Work log:** `docs/WORKLOG.md` tracks the current milestone. This plan changes only by
  dated decisions recorded in §2.
