later phases, and what the maintainer decided first. Requirement statuses live only in the
`Status` column of [requirements.md](../requirements.md); where this plan says a requirement
"ends `DONE`" or "stays `WIP`", that is the target at the phase exit.

**Size.** P6 tags 46 requirements (44 `MUST`, 2 `SHOULD`); P5 tagged 59. P6 also completes
about twelve earlier requirements that waited for it (§3.3), and §2.1 adds the secure
gateway and remote security configuration. Almost everything is new code: today the device
holds a random secret and sends a bearer token, the manifest has only the `targets` role,
and there is no attestation, DPoP, pinning, RASP or secure UI (§5.0). Much of it is Kotlin,
Swift and cryptography. P6 is about the size of P5.

## 1. Goal and exit criteria

**Goal (spec §5.1).** P6 delivers:

- hardware-backed device keys (StrongBox or TEE, Secure Enclave), with a flagged software
  key only where the profile allows it;
- device registration by challenge and response, with Android Key Attestation, Play
  Integrity and App Attest, a development provider for non-production environments,
  assurance levels `AL0`–`AL3`, periodic and risk-driven re-attestation, and revocation;
- DPoP (RFC 9449) on every device request, with nonces and a replay cache shared by every
  `api` replica, and sender-constrained access tokens (RFC 9068, `cnf.jkt`);
- strong customer authentication: a second, user-authenticated hardware key that signs
  transactions with dynamic linking, verified only by the Plux server (B13);
- the **secure gateway**: device requests to customer APIs go through the Plux server by
  default, which enforces DPoP, assurance, user identity and SCA before forwarding; a data
  source can opt into calling its API directly (B13);
- **remote security configuration**: every security setting has a default on the device
  and on the server, and changes reach devices on the existing app-start manifest request,
  as a signed, versioned delta, at no extra request (B5);
- TLS 1.3 and HSTS, certificate pinning with signed pin updates, and mutual TLS between
  server roles;
- the complete TUF-style update metadata: `root`, `targets`, `snapshot` and `timestamp`
  roles, thresholds, root rotation, algorithm identifiers, development keys refused in
  production, an offline key ceremony, and a PKCS#11 signing backend;
- confidential (encrypted) bundles, and encryption at rest of every local store under
  `strict` and `maximum`, with hardware-wrapped keys and hardware-accelerated AES;
- the `plux_security` package (RASP) with policy-driven responses;
- secure widgets (`SecureTextField`, `SecurePinPad`, `OtpInput`, `BiometricButton`), secure
  pages (screenshot and recording blocking, app-switcher blur, overlay filtering, inactivity
  lock), and masking of `sensitive` values, including on form fields;
- security profiles as presets with an effective configuration per release, which plugins
  and pages can only tighten;
- signed audit checkpoints and `plux-server audit verify`;
- privacy: consent gating completed, configurable retention, documented processing
  activities;
- the full STRIDE threat model, the OWASP MASVS L2 + resilience checklist with evidence,
  and the security test suite.

**Exit criteria.**

1. The spec's criterion: the security test suite passes; replayed, forged, mis-bound and
   expired requests are rejected; tampered and rolled-back bundles are rejected; the MASVS
   checklist is complete with evidence (the real-device part per
   [device-trust.md](../security/device-trust.md) §3.3).
2. Definition of Done (spec §5.3) DoD-1 to DoD-9 holds, with the deferrals of §3.2. DoD-6
   for P6 means the full threat model (`SEC-000`) and the MASVS L2 + R checks with evidence.
3. Plux Bank runs under the `maximum` profile with SCA transfers through the gateway, a
   secure PIN, OTP entry, confidential bundles and RASP; Plux Express runs under `standard`
   (DoD-8).
4. Every milestone passes the milestone exit gate (§11).
5. The performance budgets of §2.1 B16 hold in CI, and the startup and sync budgets of P3
   (`NFR-001`, `NFR-002`, `NFR-006`, `NFR-007`) do not regress beyond the A/B gate with DPoP
   and attestation switched on.
6. The core package stays within its size budgets (`RT-061`, B7 of plan p5: ≤ 5 MiB per App
   Bundle download and per IPA, ≤ 10 MiB per APK). RASP ships in `plux_security`, not in
   the core.

## 2. Decisions

### 2.1 Answers (maintainer, 2026-10-07)

The maintainer was asked twenty questions (D1–D20, in the work log's hand-off note of
2026-10-07) and answered them on 2026-10-07. Each answer below is final; the ADR it names
records the design in S0, and the specification changes of §4.1 implement it.

| # | Decision |
|---|---|
| B1 | **One branch, milestones, two checkpoints (D1).** P6 is developed on one branch, `feat/phase-6`, started from `main`, merged by one pull request at the phase exit (as P5's B3). Two internal checkpoints: after S3 (device trust: keys, registration, attestation, tokens, DPoP), the maintainer reviews before S4 starts; after S8 (gateway and SCA), again. |
| B2 | **Attestation is proved in three layers (D2),** written down in [device-trust.md](../security/device-trust.md) §3: (1) the verifiers in CI against recorded and synthetic test vectors; (2) the development provider (`SEC-008`) on emulators and simulators in the device jobs; (3) the maintainer's real-device check, once per phase and before a release. `SEC-002`, `SEC-003` and `SEC-004` end `DONE` only after layer 3 passes. |
| B3 | **Real devices for MASTG (D3).** CI covers what emulators and simulators can show. A real-device checklist (`docs/security/real-device-checklist.md`, S11) is the maintainer's manual step on a Pixel-class Android phone and an iPhone; the evidence goes to `docs/security/evidence/`. `SEC-190` ends `DONE` with that evidence. |
| B4 | **Devices without secure hardware (D8),** written down in [device-trust.md](../security/device-trust.md) §2: under `standard` a flagged software DPoP key is accepted and capped at `AL1`; `strict` and `maximum` refuse it at registration (`PLX-6001`, `KEY_NOT_HARDWARE_BACKED`). The setting `allowSoftwareKeys` lets an operator refuse it under `standard` too. `SEC-001` gains this rule (an ADR, since it is a `MUST`: ADR-0012). |
| B5 | **Everything is configurable, and configuration rides on the app-start request (D5, maintainer's design).** Every security setting has a default built into the runtime and the server, generated from one source so they agree. An operator changes settings per app and environment (the API and CLI now, Studio in P11). On app start the device sends the version of the settings it holds with the manifest request it already makes; if nothing changed the server sends nothing; otherwise it sends only the changed fields and the new version, and the device applies them. The design is in §5.4 (ADR-0053). Two refinements of the maintainer's design, accepted: a **version number** instead of an updated-at time (clocks on phones and servers disagree, and two edits can share a second), and the changes are bound to the **signed** manifest by a hash, so nobody can alter them in transit. Server-only settings (token lifetime, nonce rotation, the `iat` window) never travel to the device. |
| B6 | **Token refresh (D5).** Access tokens default to 5 minutes (`SEC-020`, max 15). Every refresh carries a fresh DPoP proof. On iOS it also carries an App Attest assertion (cheap, local). On Android it carries a Play Integrity token only at re-attestation: every 24 hours, on app update, on a risk signal, or when the server asks; in between, the hardware-bound DPoP key is the proof of possession. This keeps Play Integrity within its daily quota. Every value here is a setting (B5): token lifetime, re-attestation interval, and whether Android refresh always needs Play Integrity. `SEC-025` changes accordingly (ADR-0012). |
| B7 | **Play Integrity is verified locally (D6):** the server decrypts and verifies the token with the keys from the Play Console, so a self-hosted or air-gapped installation needs no call to Google per request. Google's decode API is not used. |
| B8 | **Assurance levels on iOS (D7),** written down in [device-trust.md](../security/device-trust.md) §1: a valid App Attest key and a Secure Enclave DPoP key give `AL2`; `AL3` adds Apple's fraud-metric receipt under a configured threshold and no RASP finding. `SEC-007` gains the iOS mapping. |
| B9 | **Replay cache (D9).** The replay cache holds the IDs (`jti`) of DPoP proofs already seen, shared by every `api` replica in Valkey, so a captured request cannot be sent twice. It is architected not to go down: the Valkey client supports Sentinel failover and replicas, every replica watches its health, and the runbook covers recovery. If it is unavailable nonetheless: under `maximum`, device requests are refused (fail closed); under `standard` and `strict`, each replica falls back to its own in-memory cache with a narrower `iat` window and raises a distinct alert, never accepting requests unchecked. `SEC-023` changes accordingly (ADR-0012). |
| B10 | **Confidential bundles (D10).** A confidential release ships its sections encrypted (AES-256-GCM, a per-release content key wrapped to each eligible device's hardware key-agreement key). Deltas are off for confidential releases: each changed bundle downloads whole. On the device, sections stay encrypted at rest and are decrypted into memory off the UI isolate, once per launch, on first use, with the platform's hardware-accelerated AES (B15). Encrypted deltas may come later as an optimisation, with their own ADR. `SEC-053` gains these rules (ADR-0055), and ADR-0003, ADR-0029 and ADR-0030 are revised. |
| B11 | **Update metadata (D11):** `root` signed by 2 of 3 offline keys; expiries: `timestamp` 24 hours, `snapshot` 7 days, `targets` 30 days, `root` 1 year; every value a server setting. Offline, a device keeps running its last good release; expiry is enforced when the device syncs, never by stopping a running app. Older runtimes ignore the new roles (additive, `BND-000`). The key ceremony is a runbook (`docs/runbooks/key-ceremony.md`). `SEC-050` and `SEC-121` gain the parameters (ADR-0054). |
| B12 | **Signing backends (D12):** a PKCS#11 helper process (ADR-0026's cgo-free design), tested with SoftHSM in CI; cloud KMS products are reached through their PKCS#11 libraries (AWS CloudHSM, Google Cloud HSM via `libkmsp11`, Azure Managed HSM), and Vault Transit stays. `SEC-120`'s list changes accordingly (ADR-0060). |
| B13 | **The secure gateway and transaction signing (D14, maintainer's design).** (1) **Signatures are checked only on the Plux server.** A strong-customer-authentication signature (`SEC-027`, `SEC-028`) is verified by the Plux server and nowhere else; a transaction call can only travel through the Plux server, which verifies the signature and the dynamic linking, then forwards the call to the customer's transaction service over an authenticated and authorised service-to-service connection. No customer backend verifies device signatures, and no direct path exists for transaction calls. (2) **Every other call is configurable per data source:** through the Plux server (the default) or directly from the device to the API (an opt-in per data source). The gateway costs one extra hop and makes the Plux server part of the request path; the maintainer accepts that cost and asks for performance from the start (§5.8, B16). New requirements `SEC-030`–`SEC-032` (§4.1), ADR-0056. |
| B14 | **Profiles in P6 (D13):** presets for every setting that exists in P6; settings that later phases build (publish approvals and required Plux tests in P9, accessibility blocking in P8, session replay in P11, device-placed functions in P7) join their preset in that phase. Plux Bank runs `maximum` for every setting that exists. `SEC-180`'s "visible in Studio" is met in P11; in P6 the effective configuration is visible through the API, the CLI and each release's metadata. |
| B15 | **Encryption at rest (D18) and performance:** under `strict` and `maximum` every local store is encrypted: the database, the response cache, the outbox, `persisted` state and the key-value store (`SEC-073`). Keys are unwrapped from secure hardware once per launch and kept in memory, never per read or write. AES-GCM moves from pure Dart (`DartAesGcm`, measured ten times slower in P5's B6) to the platform's hardware-accelerated implementation through FFI (ADR-0058 decides between CryptoKit/Conscrypt and a vendored audited C library, by measurement). A benchmark gates the cost (B16). P5's B6 (plain `persisted` under every profile) is superseded for `strict` and `maximum`. |
| B16 | **Performance budgets** (proposed here, approved with the plan, recorded in §30.2 in S0): DPoP proof on the device ≤ 15 ms p95 (`NFR-012`); decrypting a confidential bundle ≤ 10 ms per MiB p95 on the mid-tier device (`NFR-013`); the gateway adds ≤ 5 ms p95 per request at the server, excluding the upstream's own time, at 1,000 requests per second per replica (`NFR-025`); DPoP and token verification ≤ 1 ms p95 at the server (part of `NFR-025`); encrypted stores within 10% of the plain stores in the P5 database and state benchmarks. CI gates each A/B; absolute numbers on the reference device come from the maintainer's run. |
| B17 | **Other spec gaps, as recommended:** devices and registrations from before P6 are replaced outright, not migrated (no runtime is published and nothing runs in production; the old RPCs are refused once the new ones exist) (D4); certificate pins come from `PluxConfig` at build time (at least two, one a backup key) and are updated only through signed update metadata, a mismatch fails closed and is reported (`SEC-041`, D17); `SEC-026` delivers the token-exchange endpoint and user-token forwarding to data sources and the gateway in P6, the function side in P7 (D15); `SEC-043` delivers TLS 1.3 and HSTS at the edge, TLS to PostgreSQL and Valkey, and mutual TLS on internal HTTP between roles in P6, `fnrunner` in P7 (D16). |
| B18 | **Dependencies (D19),** each with its ADR, licence, maintenance and size checked before use (`dependencies.md` §1): Android `com.google.android.play:integrity` and `androidx.biometric`; Go `github.com/go-jose/go-jose/v4` for JWS and JWE, and a CBOR decoder for App Attest (`github.com/fxamacker/cbor/v2`, or a minimal in-house decoder if the ADR finds it smaller and safer); `github.com/miekg/pkcs11` in the PKCS#11 helper only (never in `plux-server`); SoftHSM2 as a CI test tool. iOS uses system frameworks only (DeviceCheck, CryptoKit, LocalAuthentication, Security). RASP is Plux's own code; no third-party RASP SDK. The Play Integrity library's licence is the Play terms, not an open-source licence: like ML Kit in P5 (B5(4) of plan p5), the maintainer accepts those terms in the dependency ADR before it is used. |
| B19 | **Items carried over from P5 (D20):** (a) guards read app and plugin state, alongside real assurance levels (`NAV-009`, the navigation reference's promise); (b) form fields can be tagged `sensitive`, an additive schema change; (d) ADR-0046 is corrected from `old` to `previous`; (e) `OtpInput` is re-tagged P6 under `SEC-090`, with platform autofill (Android SMS User Consent, iOS one-time-code), manual entry, configurable length and alphabet, paste with format check, and a completion event; (f) the build leftovers in the agent container's `/usr/local` are ignored. |
| B20 | **`SCH-012` is checked, not assumed (D20 (c)).** S0 checks every requirement that mentions crash reports or session replay. Session replay is P11's (`SEC-161`'s `replay` category); if crash reports also belong to a later phase, `SCH-012` stays `WIP` with that phase named, or is split into its P1 part (`DONE`) and the later part, as the maintainer prefers. It is marked `DONE` only when nothing it requires is left unbuilt. |
| B21 | **Scanner size (2026-10-07).** `plux_scanner` stops bundling ML Kit's barcode model (about 2.4 MB per Android app). On Android it uses ML Kit through Google Play services (unbundled, about 200 KB) whenever Play services is available, and asks for the model's download at the first app open, in the background, so scanning is ready before first use. Where Play services is missing or the model cannot be downloaded (for example Huawei devices, or no network on first open), it falls back to ZXing-C++ through FFI (Apache-2.0, offline, a few hundred KB per ABI, measured in the ADR). iOS keeps Apple's Vision and AVFoundation (no size cost). Both engines are measured on one test set of codes, including damaged, blurred, small and badly lit ones, and the results are recorded. ADR-0051 is revised; ZXing-C++ gets its dependency ADR. Milestone S10. |

Earlier decisions that hold for P6:

- **Additive evolution only** for the bundle format, manifest, document schema and API
  (`BND-000`, `SCH-000`, `SRV-000`). New update-metadata roles, settings, gateway routes and
  widget props are additions; a bundle that needs them declares `required_features`.
- **Limits come from the registry** (`LIM-001`): gateway request and response sizes,
  timeouts and rates, SCA challenge lifetime, configuration size, confidential bundle size
  are registry entries before code reads them.
- **Security capabilities are never gated by edition** (`GOV-032`): everything in P6 is in
  the open core.
- **Verify before load** (`SEC-052`): a confidential bundle is verified (hashes over the
  ciphertext, signed by `targets`) before it is decrypted.

### 2.2 Questions for the start of S0

Found while writing this plan; each has a recommendation, and none blocks S0's other work.

**Answered (maintainer, 2026-10-07): every recommendation approved.** Q1: the DPoP key's
storage is measured in S1; if StrongBox misses `NFR-012`'s 15 ms p95, the DPoP key moves
to the TEE and StrongBox holds the SCA key, with the `SEC-001` change and ADR-0012 updated
in the same change series (spec 1.4.0 already allows it, §15.2). Q2: the profile setting
`allowDirectDataSources` (`SEC-030`): allowed under `standard` and `strict` with the compile
warning `DIRECT_SOURCE_ASSURANCE_UNENFORCEABLE`, refused under `maximum` (`PLX-6063`).
Q3: overrides only tighten a profile's preset, for operators as for plugins and pages
(`SEC-181`, `SEC-182`); loosening means choosing a lower profile, which is audited and
visible in each release's effective configuration (`PLX-6041`).

| # | Topic | Question and options | Recommendation |
|---|---|---|---|
| Q1 | StrongBox and DPoP speed | `SEC-001` says the DPoP key lives in StrongBox where available. StrongBox signs far slower than the TEE (tens to hundreds of milliseconds), and with the gateway every API call carries a DPoP proof. Options: (a) DPoP key in StrongBox where available, as written; (b) DPoP key in the TEE, SCA key in StrongBox where available; (c) measure in S1 and decide. | (c), defaulting to (b) if StrongBox misses `NFR-012`'s 15 ms p95: the TEE is still secure hardware and still gives `AL2`; StrongBox protects the key that signs money. A spec change to `SEC-001` if (b). |
| Q2 | Direct calls under `maximum` | B13 lets a data source call its API directly. Under `maximum`, should direct calls be allowed? | A profile setting `allowDirectDataSources`: allowed under `standard` and `strict` (with a compile warning when the source requires an assurance level, since the server cannot enforce it on a direct call), refused under `maximum`. |
| Q3 | Settings that loosen | B5 makes every setting configurable. May an operator loosen a setting below the app's profile preset (for example a longer token lifetime under `maximum`)? | No: within each setting's hard bounds, an override can only tighten the profile's preset (`SEC-181`'s rule, applied to operators too). To loosen, choose a lower profile, which is visible in the release's effective configuration and audited. |

### 2.3 S0 record (2026-10-07)

- **Error codes.** The registry holds one reason per code (`error-handling.md`), so B4's
  "`PLX-6001`, reason `KEY_NOT_HARDWARE_BACKED`" and device-trust.md's development-provider
  refusal get their own codes: `PLX-6003` `KEY_NOT_HARDWARE_BACKED` and `PLX-6004`
  `DEV_PROVIDER_IN_PRODUCTION`; device-trust.md is updated. The P6 codes are
  `PLX-6001`–`6016`, `6020`–`6022`, `6040`–`6042`, `6050`, `6060`–`6064`, `6070`–`6073`,
  `6100`, and the compiler warning `PLX-1504` `DIRECT_SOURCE_ASSURANCE_UNENFORCEABLE`.
- **Limits.** The registry has no seconds unit, so `sca.challengeLifetime` is in
  milliseconds (300,000).
- **Required features.** No central registry of feature keys exists: the compiler emits
  a key only when a document uses the feature. Each `*.v1` key of §4.3 is therefore added
  by the milestone that builds its feature (S4, S7, S8, S10), with the runtime's list in
  `packages/plux_flutter/lib/src/core/features.dart`.
- **Telemetry.** `rasp_detection` existed; `attestation_result` and `pin_failure` are added
  (spec Appendix G).
- **`SCH-012` (B20).** Checked: crash reports are grouped and symbolicated by `ANL-040`
  (P9) and session replay is `ANL-050` (P11, `SEC-161`'s `replay`); the encrypted-storage
  part is P6's (`SEC-073`). `SCH-012` therefore stays `WIP` after P6, naming P11 as the
  phase that completes it, unless the maintainer prefers a split.
- **Approved (maintainer, 2026-10-07):** S0 as delivered, including `PLX-6003`/`PLX-6004`,
  `SCH-012` staying `WIP` naming P11, and `signTransaction` reviewed in S8.
- **Device CI (maintainer, 2026-10-07):** the device end-to-end jobs (iOS 46 min, Android
  26 and 35 about 14 min each in run 37613709956) run one parallel job per flow
  (starter, generated, hosts, bank, express; iOS runs express and generated as one job, within GitHub's five concurrent macOS jobs; the add-to-app hosts start Flutter with the app, the cause of most device-job failures), with build caches that only a passing run
  on `main` saves; target 13 to 15 minutes (ADR-0043, Revision). The add-to-app online
  flow's back taps landed during the page's route transition and missed the button, so
  the page stayed open, no safe point came and the update never activated (run
  37623043856); the flow now closes a page only once its transition has ended.
- **Not in S0.** The threat model's structure (`SEC-000`) and benchmark groundwork move to
  S1, where the first benchmark (`NFR-012`) is built.

## 5. Architecture

### 5.0 Starting point (surveyed 2026-10-07)

| Area | What exists | What P6 replaces or adds |
|---|---|---|
| Device identity | `RegisterDevice` returns a random secret; the server stores its hash; a 15-minute opaque bearer token (`plux_dat_…`), no revocation | Hardware keys, attestation, RFC 9068 tokens, DPoP, revocation |
| Device storage | AES-GCM key in AndroidKeyStore (not StrongBox), Keychain on iOS, over `dev.plux/runtime` | P-256 signing and key-agreement keys in secure hardware |
| Config | `auth.device` access 5 min / refresh 30 days in config, unused; the token TTL is a constant | Settings model and remote configuration (B5) |
| Update metadata | `targets` only, Ed25519, 7-day expiry, any one valid signature | Four roles, thresholds, rotation |
| Signing backends | File (development), Vault Transit | PKCS#11 helper |
| Encryption at rest | `secure` state, outbox, optional cache, SQLCipher, all with pure-Dart AES-GCM; `persisted` plain | Every store under `strict`/`maximum`, native AES, hardware-wrapped keys |
| Secure UI | `security.secure` blocks clipboard writes only; `requiresAssurance` exists, guards read assurance as 0 | Secure widgets, secure pages, real levels |
| Profiles | The enum compiled into the bundle; only the database reads it | Presets, effective configuration, tightening |
| Audit | Hash chain per organisation, `VerifyChain` unused outside its package | Signed checkpoints, `plux-server audit verify` |
| Consent | `Plux.setConsent`, gating `analytics` and `experiments` | Retention configurable, processing activities documented |
| Cache | `memory` or `valkey`, TLS 1.2 minimum to Valkey | Sentinel failover, the replay cache |

### 5.1 Device keys (S1) — ADR-0012

- **Native key service** in `plux_flutter`'s Kotlin and Swift code, behind a Dart
  `DeviceKeys` interface:
  - DPoP key: P-256, non-exportable, StrongBox then TEE on Android (subject to Q1), Secure
    Enclave on iOS; a software key only per B4.
  - Key-agreement key: P-256 ECDH in secure hardware, for confidential bundles (S7).
  - SCA key: P-256, user authentication required for every use (Android
    `setUserAuthenticationParameters(0, BIOMETRIC_STRONG | DEVICE_CREDENTIAL)`; iOS
    `.biometryCurrentSet` access control), created on enrolment (S8).
  - Key Attestation certificate chains requested with the server challenge on Android.
- **DPoP proofs** built in Dart (header, claims) and signed natively; the signature is the
  only native call. Proofs are created off the UI isolate. The channel uses a binary codec;
  if the method channel's cost shows in `NFR-012`, the signing call moves to FFI (JNI on
  Android, `@_cdecl` on iOS).
- **Key loss** (factory reset, backup restore to a new device, key invalidated by a new
  biometric enrolment) leads to re-registration, never to a software fallback where the
  profile forbids it.

### 5.2 Registration and attestation (S2) — ADR-0012

- **Flow (`SEC-005`):** `CreateRegistrationChallenge` (single use, TTL ≤ 5 minutes, stored
  in the cache) → the device creates or loads its keys and gathers evidence → `RegisterDevice`
  → verification → device record (`device_id`, `jkt`, platform, app build, key storage,
  attestation results, assurance level).
- **Android Key Attestation (`SEC-002`):** chain to Google's roots (embedded, rotatable by
  configuration), challenge, `attestationSecurityLevel` and `keymasterSecurityLevel`,
  verified boot state, bootloader lock, package name, signing certificate digest; the
  revocation list fetched on a schedule by the `worker`, cached, and configurable for
  air-gapped installations (a file the operator updates).
- **Play Integrity (`SEC-003`):** standard requests with a request hash of the challenge and
  the `jkt`; decrypted and verified locally (B7); verdicts mapped per profile.
- **App Attest (`SEC-004`):** attestation object verified to Apple's App Attest root;
  nonce, App ID, environment (`development`/`production`), counter stored; assertions on
  sensitive requests with a strictly increasing counter; the fraud-metric receipt refreshed
  by the `worker` for `AL3` (B8).
- **Development provider (`SEC-008`):** a named provider, accepted only by non-production
  environments ([device-trust.md](../security/device-trust.md) §3.2).
- **Assurance (`SEC-007`):** computed by the server from the evidence, profile and RASP
  reports; carried in the token.
- **Re-attestation and revocation (`SEC-006`):** every 24 hours by default, on app update,
  on a RASP report or anomaly, and on request (`use_reattestation` error); `RevokeDevice`
  forces re-registration; revoked `jkt`s are refused at once on every replica.
- **Outage policy (`SEC-009`):** `failClosed` or `grace(duration)` with the last known level,
  per profile and setting.

### 5.3 Tokens and DPoP (S3) — ADR-0012

- **Access tokens (`SEC-020`):** RFC 9068 JWTs, ES256, signed by a server token key through
  the signing abstraction, with `cnf.jkt`, device ID, app ID, environment and assurance
  level; 5 minutes by default, at most 15.
- **Proofs (`SEC-021`, `SEC-022`):** `typ`, `alg`, `jwk`, `htm`, `htu` (normalised),
  `iat` (±60 s by default), `jti`, `ath`, `nonce`; verified in one middleware for every
  device route: manifest, control, telemetry, token refresh, gateway, and later functions and
  dev sessions.
- **Replay cache (`SEC-023`, B9):** `SET NX` with the window's expiry in Valkey; Sentinel
  failover in the in-house client; per-replica fallback under `standard` and `strict`; fail
  closed under `maximum`; health metric, alert and runbook.
- **Nonces (`SEC-024`):** server nonces rotated at least every 5 minutes, derived from a
  rotating secret so every replica accepts them without shared state; `DPoP-Nonce` on
  responses; `use_dpop_nonce` makes the client retry once.
- **Refresh (`SEC-025`, B6):** a fresh proof plus the platform evidence B6 names; no
  long-lived bearer refresh tokens.
- **The old flow** (device secret, bearer token) is removed from the runtime and refused by
  the server (B17).
- **Negative suite (`SEC-029`):** every case the requirement lists, plus software keys where
  hardware is required, revoked devices and development evidence in production.

### 5.4 Remote security configuration and profiles (S4) — ADR-0053

- **One source of settings:** `schema/security/settings.json` lists every setting: type,
  unit, per-profile default, hard bounds, tighter direction, and audience (`device`,
  `server` or both). `make gen` produces the Go and Dart defaults, so the runtime and the
  server always agree on the built-in values.
- **Effective configuration:** profile preset → app and environment overrides (only
  tightening, Q3) → plugin and page tightening (`SEC-181`, at compile time). The release
  records the effective configuration in its metadata (`SEC-180`).
- **Versions:** each change an operator makes creates a new version (an increasing integer
  per app and environment) and an audit entry (`SEC-140`); later phases add approval (P9).
- **On the wire (the maintainer's design, B5):**
  1. The device sends `config_version` with its manifest request: `0` when it runs on its
     built-in defaults, otherwise the version it last applied.
  2. If the manifest's ETag matches (`if_none_match`), the server answers `not_modified` as
     today: nothing at all is sent.
  3. Otherwise the signed manifest carries `config: {version, hash}`. If the device's
     version equals it, nothing more is sent. If it differs, the response carries
     `config_patch`: an RFC 7396 JSON merge patch from the device's version to the current
     one, or the operator's overrides when the device sends `0`.
  4. The device applies the patch to its stored settings, checks the SHA-256 of the result
     against the signed hash, and stores the result with its version. On a mismatch it asks
     again with `config_full_required`; the server then sends the whole override set.
  5. The server keeps a bounded history of versions to build patches; a device older than
     the history gets the full override set.
- **Why this way:** it adds a few bytes to the request the device already sends at start,
  inside `NFR-006`'s 1 KiB budget; nothing is sent when nothing changed; a change travels as
  only the changed fields; the hash in the signed manifest stops anyone from altering
  settings in transit, the same way signed bundle hashes protect deltas (`SYN-011`).
  Alternatives considered, in the ADR: updated-at timestamps (clock skew, ties), a separate
  configuration endpoint (an extra request per start), silent push (unreliable, a new
  dependency), sending the whole configuration each time (wasteful).
- **Applying a change:** settings that shape a running session (RASP responses, screenshot
  policy, inactivity lock, pins) apply at once; settings bound to keys or registration
  (software keys, attestation) apply at the next registration or refresh. Stored settings
  are re-verified against the last verified manifest at launch.
- **Server-only settings** (token lifetime, `iat` window, nonce rotation, replay-cache
  fallback, gateway limits) are read by the server from the same store and never sent.
- **Device-specific state** (revoked, assurance level, re-attestation due) reaches the
  device through token responses and errors, not through configuration.
- **Tools:** `plux security config show|set|diff` in the CLI and the matching API; Studio
  shows and edits them in P11.

### 5.5 Update metadata, signing backends and audit (S5) — ADR-0054, ADR-0060

- **Roles (`SEC-050`):** `root` (2 of 3 offline keys, 1 year), `targets` (bundle hashes and
  release contents, 30 days), `snapshot` (current metadata versions, 7 days), `timestamp`
  (latest snapshot, 24 hours), every expiry a server setting (B11). The `timestamp` and
  `snapshot` are re-signed by the `worker` before expiry.
- **The device** verifies the chain `timestamp` → `snapshot` → `targets` → manifest, with
  thresholds per role, and keeps its last good release when offline or when the metadata is
  expired at sync (B11). Older runtimes keep reading the manifest's `targets` signature.
- **Root rotation (`SEC-051`):** a new root is accepted only when signed by the previous
  root's threshold and its own; the chain of roots since the embedded one is fetched in
  order (`GetRootKeys`).
- **Development keys (`SEC-056`):** each key carries its environment type; a production
  runtime refuses development-signed metadata.
- **Algorithm identifiers (`SEC-122`):** every signature and key names its algorithm;
  ECDSA P-256 is the second algorithm (ADR-0004); the post-quantum path is a key type the
  metadata can name (ML-DSA) and a dual-signature transition, written down in the ADR, not
  implemented.
- **Pins (`SEC-041`)** travel in the signed metadata (B17).
- **PKCS#11 helper (`SEC-120`, B12):** a separate binary with `miekg/pkcs11`, talking to
  `plux-server` over a local socket; tested with SoftHSM2; cloud HSMs through their PKCS#11
  libraries.
- **Key ceremony (`SEC-121`):** `docs/runbooks/key-ceremony.md`: generating root keys
  offline, the 2-of-3 signing, rotating online keys without an app release, recovering from
  a lost or compromised key; rehearsed once with SoftHSM in a test.
- **Audit checkpoints (`SEC-141`):** the `worker` signs a checkpoint of each organisation's
  chain head on a schedule; `plux-server audit verify` checks the chain and the checkpoints
  and reports the first broken entry.

### 5.6 Transport (S6)

- **Edge (`SEC-040`):** TLS 1.3 only by default, TLS 1.2 with AEAD ciphers only by
  configuration, HSTS on every response; the Compose stack's proxy and the server's own TLS
  configured alike.
- **Pinning (`SEC-041`, `SEC-042`):** SPKI SHA-256 pins on the runtime's HTTP clients
  (Cronet and `URLSession` through their pinning hooks, `dart:io` for the rest), at least two
  pins, updates through signed metadata, mismatch fails closed and reports `pin_failure`;
  optional pins for customer domains reached directly, from the app document.
- **Internal (`SEC-043`):** mutual TLS between roles over HTTP, from an internal CA the
  operator provides (or the platform's mesh); TLS to PostgreSQL and Valkey required in
  production environments.

### 5.7 Encryption at rest and confidential bundles (S7) — ADR-0055, ADR-0058

- **Native AES-GCM (B15):** one FFI entry point in `plux_native` for encrypt and decrypt,
  backed by the implementation ADR-0058 chooses after measuring CryptoKit and Conscrypt
  against a vendored audited library; Dart's `cryptography` stays only for tests and
  desktop development.
- **Keys:** a per-installation data key wrapped by a hardware key (Android Keystore AES key
  or the key-agreement key; iOS Secure Enclave via ECIES), unwrapped once per launch and
  held in memory for the session.
- **Stores (`SEC-073`):** the database (SQLCipher key), the response cache, the outbox,
  `persisted` state and the key-value store, all encrypted under `strict` and `maximum`;
  under `standard`, as P5 left them unless the app asks for more. Existing plain stores are
  migrated in place on the first launch under a stricter profile, atomically.
- **Tokens and keys (`SEC-072`):** only in Keystore- or Keychain-protected storage; a test
  scans the app's files after a session for any token, key or secret.
- **Confidential bundles (`SEC-053`, B10):** the `worker` encrypts each section of a
  confidential release with a per-release AES-256-GCM key; hashes in `targets` cover the
  ciphertext, so verification comes before decryption (`SEC-052`); the content key is
  wrapped to each eligible device's key-agreement key (assurance level from the settings)
  and delivered with the manifest; deltas are off; on the device, sections stay encrypted on
  disk and are decrypted into memory off the UI isolate, once per launch, on first use, and
  the reader works on the decrypted buffer instead of the mmap for those sections.

### 5.8 Secure gateway, user identity and SCA (S8) — ADR-0056

- **Routing (`SEC-030`):** each data source's `route` is `plux` (default) or `direct`. A
  `plux` request goes to the gateway with the device's token and DPoP proof; the gateway
  finds the upstream registered for the data source, app and environment, and forwards.
  A `direct` request goes from the device to the API, as in P5, within the network domain
  rules (`DAT-030`) and optional pins (`SEC-042`). Under `maximum`, direct is refused (Q2).
- **What the gateway checks before forwarding:** the token and DPoP proof (S3); the
  assurance level the data source, page or route requires; the plugin's capability to call
  the source (`SEC-080`); request size and rate limits; for transaction operations, the SCA
  signature (below).
- **Upstreams (`SEC-031`):** registered on the server per app and environment: base URL,
  authentication (mutual TLS client certificate, OAuth 2.0 client credentials with the
  access token cached until expiry, or a header key), timeouts, allowed methods. Credentials
  are encrypted (`SEC-106`). Base URLs of `plux` sources live on the server, not in the
  bundle. Private and link-local addresses are refused unless the upstream allows them
  (self-hosted customers with internal APIs). The gateway adds a `Plux-Assertion` header: a
  short-lived JWT signed by the server with the device, app, environment, assurance level,
  verified user (after token exchange) and a hash of the request.
- **User identity (`SEC-026`):** the host's user token is exchanged (RFC 8693) for a token
  the gateway forwards, verified against the customer's identity provider's JWKS (a test
  identity provider in `test/refapi`).
- **SCA (`SEC-027`, `SEC-028`, `SEC-032`, B13):**
  1. Enrolment: the device creates the SCA key (user authentication required), the server
     verifies its Key Attestation or App Attest binding and stores the public key.
  2. A transaction: `signTransaction` asks the server for a challenge, shows the amount,
     currency and payee exactly as they will be signed, asks for biometrics or the device
     credential, and signs the canonical payload (the displayed fields, the challenge and the
     operation) with the SCA key.
  3. The device sends the operation through the gateway with the signature. The gateway
     verifies the signature, the challenge (single use, short TTL from the registry), and
     that the operation's amount, currency and payee equal the signed ones, using the data
     source's SCA mapping (§4.3).
  4. Only then does the gateway forward to the customer's transaction service, over the
     upstream's authenticated connection, with the verified assertion. The transaction
     service never verifies device signatures, and a transaction operation declared
     `direct` is a compile error.
- **Streams and transfers:** WebSocket and SSE are proxied by the gateway, and uploads and
  downloads stream through it without buffering whole bodies. The outbox replays through
  the gateway with its idempotency keys.
- **Performance (B16):** pooled HTTP/2 connections per upstream, streamed bodies (only an
  SCA operation's body is read, bounded by the limit), the DPoP key parsed once per token,
  no body logging; it runs in the `api` role and can run as its own `gateway` role
  (ADR-0006) to scale separately. `NFR-025` gates its added latency in CI.
- **Privacy:** the gateway keeps no bodies, logs no payloads, and records only metrics and
  audit entries for administrative changes (`SEC-160`).

### 5.9 RASP — `plux_security` (S9) — ADR-0057

- **Detections (`SEC-070`):** root and jailbreak, hooking frameworks (Frida, Xposed and
  LSPosed, Substrate), debugger attachment, emulator and simulator, repackaging (signing
  certificate mismatch), untrusted installer, screen mirroring or recording, overlays
  (tapjacking), accessibility services with suspicious capabilities; Plux's own Kotlin and
  Swift checks, run off the UI thread at start and periodically.
- **Responses (`SEC-071`):** `report`, `warn`, `degrade` (pages and functions requiring
  `AL3` disabled) or `block` (a blocking screen), per detection, from the settings (B5).
  Every detection is reported (`rasp_detection`) and lowers the device's level at the server;
  a detection under a profile that requires re-attestation triggers it.
- **Honesty:** RASP raises the cost of an attack; it does not stop a determined attacker on
  a device they control. The guide and the threat model say so.

### 5.10 Secure UI (S10) — ADR-0059

- **Widgets (`SEC-090`):** `SecureTextField` (no suggestions, autocorrect, clipboard,
  keyboard learning; obscured; incognito keyboard flags on Android, secure text entry on
  iOS); `SecurePinPad` (optional randomised layout, no key-press animation, haptics only);
  `OtpInput` (B19 (e)); `BiometricButton` (biometric step-up); `KycCameraCapture` in
  `plux_media` (framing guides and quality checks).
- **Secure pages (`SEC-091`, `SEC-093`, `SEC-094`):** `FLAG_SECURE` on Android while a
  secure page shows; on iOS, a covering view while capture is detected and in the app
  switcher; touch filtering when obscured on Android; the inactivity lock with biometric or
  device-credential re-authentication after a configured idle time.
- **Masking (`SEC-092`):** `sensitive` values masked unless the user unmasks them, and
  excluded from telemetry and traces; `sensitive` on form fields (B19 (b)).
- **Actions:** `biometricAuth` (with the `biometrics` capability, ADR-0051) and
  `signTransaction` (§5.8).

### 5.11 Reference apps, release builds, privacy and verification (S11)

- **Plux Bank** under `maximum`: registration with attestation (development provider in CI),
  SCA transfers through the gateway, `SecurePinPad`, `OtpInput`, confidential bundles,
  secure pages, RASP `block`; **Plux Express** under `standard`, with direct and gateway
  sources side by side. `test/refapi` gains a transaction service that trusts only the
  gateway's assertion, and a test identity provider.
- **Release builds (`SEC-074`, `DEV-050`):** a CI test builds a release APK and IPA and
  inspects them for dev tooling, verbose logging and source maps.
- **Privacy (`SEC-160`, `SEC-161`):** pseudonymous device IDs checked, telemetry retention a
  setting, processing activities documented in `docs/security/privacy.md`.
- **Verification (`QA-008`, `SEC-190`):** the DPoP and attestation negative suite; tamper and
  rollback attacks against every metadata role and confidential bundles; authorisation
  matrix tests for every role and permission; an OWASP ZAP baseline scan of the API (Studio's
  scan in P11); fuzzing of DPoP proofs, tokens, attestation objects, CBOR and metadata
  (`QA-004`); the MASVS checklist (`docs/security/masvs.md`) with emulator evidence, and the
  real-device checklist for B3.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Native key and attestation code behaves differently across devices and OS versions | One Dart interface over small native services; Android 26 and 35 emulators and the iOS simulator in CI; the real-device check (B2) before the phase closes |
| Hardware signing makes every request slower | `NFR-012` gate from S1; Q1; proofs off the UI isolate; FFI if the channel costs too much |
| Play Integrity quota exhausted | Play Integrity only at re-attestation (B6); the interval a setting; a metric on the daily count |
| Replay cache unavailable | Sentinel failover, health alerts, the B9 fallback, the runbook |
| The gateway becomes a bottleneck or a single point of failure | `NFR-025` gate; pooled connections and streamed bodies; a separate `gateway` role to scale; the outbox retries through it; direct routes where the profile allows |
| The gateway reaches internal networks (SSRF) | Upstreams only from the server's registry; private addresses refused unless allowed per upstream; tests for each refusal |
| A configuration change loosens security or is tampered with | Tighten-only overrides (Q3); hash in the signed manifest; audit entries |
| Encryption slows the device | Native hardware AES (B15); keys unwrapped once; decryption once per launch; benchmarks gated |
| Losing a root key, or a ceremony mistake | 2 of 3 keys; the key ceremony runbook rehearsed with SoftHSM; rotation tested |
| Attestation claims made without real-device proof | [device-trust.md](../security/device-trust.md) §3.4; the three statuses stay `WIP` until the check passes |
| P6 is as large as P5 | Two checkpoints (B1); S1–S3 first; S5, S6 and S9 in parallel with S4 |

## 11. Process

- **Branch and pull request:** one branch, `feat/phase-6`, and one pull request at the phase
  exit (B1), with the two checkpoints reviewed on the branch.
- **Agents:** feature code by parallel agents in their own worktrees (`coder`; `coder-high`
  for everything touching keys, DPoP, attestation, encryption, the gateway or SCA); the lead
  merges, reviews every merge, and runs all gates centrally.
- **Milestone exit gate** (the P3–P5 gate, unchanged):
  1. every `make` gate passes locally, judged by its exit code, not its output;
  2. the end-to-end gate test passes at least 40 times with the race detector, and every
     intermittent failure is root-caused;
  3. a dispatched CI run is green in every job;
  4. the milestone's open items are fixed or put to the maintainer;
  5. the hand-off note and the report say what was verified and how.
- **Stops for the maintainer** (AGENTS §7), already known: §2.2's questions; the spec
  changes and ADRs of S0; every new dependency; the performance budgets of B16 in §30.2;
  coverage floors of new packages; new CI jobs or gates; and, by the security practices,
  every change to keys, DPoP, attestation, encryption or a security default.
- **Work log:** `docs/WORKLOG.md` tracks the current milestone. This plan changes only by
  dated decisions recorded in §2.
