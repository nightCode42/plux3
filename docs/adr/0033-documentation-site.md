# 0033. Documentation site: Starlight on Bun, published to GitHub Pages

- **Status:** Accepted
- **Date:** 2026-09-28
- **Requirements:** `DX-002`, `DX-006`, `RT-001`, DoD-7

## Context and problem

From P3 every phase must publish its user-facing documentation on a documentation site
(DoD-7, `DX-002`): concepts, a quick start, guides, the widget catalogue generated from the
descriptors, the action catalogue, the PXL reference, API references (dartdoc, Go doc,
protobuf), the security whitepaper, the compliance pack and the runbooks. Most of this
already exists as Markdown under `docs/`, and several references are generated by
`make gen`. What builds the site, from which sources, and where is it published?

## Decision drivers

- One source: the Markdown in `docs/` and the generated references stay where they are;
  the site renders them, it does not copy them into a second tree that drifts.
- A toolchain the repository already pins — Go, Flutter and Bun — rather than a new one.
- Search, dark mode, accessible output and good Markdown support without custom theming
  work.
- Links between documents that work both on GitHub and on the site, checked in CI.
- Free hosting with no account beyond the repository's own.

## Considered options

1. **Starlight (Astro), built with Bun from `docs/`, deployed to GitHub Pages by a workflow.**
2. MkDocs with Material for MkDocs.
3. Docusaurus.
4. Hugo.

## Decision

Chosen option: **1**, with `astro` 7.3.5 and `@astrojs/starlight` 0.42.4 (both MIT),
pinned in the site's lockfile. Starlight is a documentation theme for Astro with built-in
search (Pagefind, run at build time, no service), dark mode, accessible navigation and
MDX support.

- **Location.** The site project is `site/` at the repository root: `package.json`,
  `bun.lock`, `astro.config.mjs` and a content loader. It is not part of the Studio
  workspace, so neither can break the other's lockfile. Licence: Apache-2.0, like `docs/`.
- **Sources.** A content loader reads `docs/**/*.md` in place (Astro's `glob` loader with
  `base: '../docs'`), so the site renders the same files readers see on GitHub. Pages the
  site adds — the landing page and the section indexes — live in `site/src/content/`.
  Relative Markdown links are rewritten to site routes at build time, and the build fails
  on a broken internal link.
- **Generated references.** The widget and action catalogues, the error catalogue, the
  limits reference and the API description are already written into `docs/reference/` by
  `make gen`; the site renders them unchanged. The dartdoc output of `plux_flutter` is built
  by `dart doc` in the same job and published under `/api/dart/`, linked from the site; Go
  documentation links to `pkg.go.dev` for the Apache-2.0 modules; the protobuf API links to
  the generated OpenAPI description.
- **Build.** `make docs-site` runs `bun install --frozen-lockfile` and `bun run build` in
  `site/`, with Bun at the version the Makefile pins; CI builds the site on every change to
  `docs/` or `site/`, which is also the link check.
- **Publishing.** A workflow deploys the built site to **GitHub Pages** with the official
  `actions/upload-pages-artifact` and `actions/deploy-pages` actions (pinned by SHA), on
  pushes to `main` and on release tags, with `pages: write` and `id-token: write` only in
  that job. Enabling Pages for the repository (source: GitHub Actions) is a one-time
  setting for the maintainer.
- **Release notes** (`DX-006`) are generated by `git-cliff` per component, as today, and
  published as a page per release together with the upgrade guide.

## Consequences

- **Positive:** one Markdown source for GitHub and the site; the toolchain is Bun, already
  pinned; search and accessibility come built in; hosting is free.
- **Negative:** a second Bun project with its own lockfile and Dependabot entry; Astro and
  Starlight majors are upgrade decisions (Starlight is pre-1.0 and changes its API between
  minor versions).
- **Follow-up:** the quick start and host-integration guide with P3; the use-case guides
  as the features they describe arrive; versioned documentation from the first tagged
  release.

## Options in detail

### Option 2 — MkDocs Material

Excellent documentation theme, but it adds Python and pip-pinned packages to CI for the
site alone, and the project entered maintenance mode in favour of a new tool.

### Option 3 — Docusaurus

Capable and popular, but React-and-webpack heavy for a mostly static site, with slower
builds and more configuration than Starlight for the same result.

### Option 4 — Hugo

A single fast binary, but a Go-template theme ecosystem whose documentation themes offer
less out of the box (search, accessibility) and would need more custom work.
